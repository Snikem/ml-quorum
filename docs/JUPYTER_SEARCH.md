# Три замера горячего поиска из JupyterHub

Нужны Linux, Java 11+, JAR, папка готового Lucene-индекса и `linear_monomials.json`.
Notebook: `notebooks/one_query.ipynb` (имя сохранено, теперь по умолчанию три замера).
Если собираете на сервере из Git:

```bash
git pull
mvn -Prunner -DskipTests clean package
```

Команда для вашего JH (из корня репозитория; исправьте путь к модели при необходимости):

```bash
java -Xmx4g -jar target/monoforest-0.1.0-SNAPSHOT-runner.jar \
  --index /home/anglukhikhan/unpacked/lucene_index_positions \
  --model /path/to/linear_monomials.json \
  --ram-root /run/jupyter-monitor/monoforest-anglukhikhan \
  --query "grammar terms medicine" \
  --threshold 3 --limit 10 --hot true --repeat 3
```

`--hot true` выполняет последовательно:

1. Одно копирование индекса в собственную временную папку tmpfs и одно открытие индекса/модели.
2. Одну подготовку признаков запроса и объекта Lucene Query (`prepare_query_ms`).
3. Один полный прогрев того же запроса (`warmup`, отдельно от измеряемых запусков).
4. Три поиска с тем же подготовленным запросом, reader и searcher (`runs`).

Это 4 выполнения поиска: один прогрев и три измеряемых. Результаты не подменяются
сохранённой выдачей: каждый раз вызывается Lucene `search`. Кеши Lucene и JVM
между запусками не сбрасываются. Query-фичи, включая частоты TSV и BM25TopScores
при необходимости для модели, готовятся один раз. Вычисления признаков документов,
необходимые при обходе postings и ранжировании, остаются частью самого поиска.
Один прогрев не гарантирует полной стабилизации JIT/GC: приводятся все три значения,
без выбора самого быстрого. Это время повторного готового запроса, не нового текста.

## Первые N совпадений без ранжирования

Теперь runner по умолчанию возвращает первые N документов (по умолчанию 10),
для которых строго выполняется `intercept + сумма весов совпавших мономов > threshold`.
Задавайте N через `--limit N`, в notebook — `LIMIT`. Это те же условия модели,
включая отрицательные коэффициенты: совпадения одного монома недостаточно.

Коллектор работает с `COMPLETE_NO_SCORES`, не вызывает `score()` и останавливает
весь поиск сразу на N-м совпадении, включая последующие сегменты индекса.
Сумма весов внутри проверки порога всё ещё вычисляется; сортировка по ней,
очередь top-K и `explain` не выполняются. Поля `score`/`probability` отсутствуют.
Порядок — внутренние Lucene doc ID, а не релевантность; после перестройки индекса
этот порядок может измениться. Title/text читаются по внутреннему ID без повторного
поиска по внешнему ID документа.

Если достигнут N, `limit_reached=true`, `total_hits=N` и
`total_hits_relation=GREATER_THAN_OR_EQUAL_TO`: это нижняя граница, не точный итог.
Наличие N+1-го совпадения не проверяется. Если найдено меньше N, поиск доходит до
конца и `total_hits_relation=EQUAL_TO`. При редких или отсутствующих совпадениях
всё ещё может понадобиться большой обход. Ускорение на вашем индексе нужно измерить.

Прежний режим ранжирования доступен только при явном `--top-k N`.
Одновременно `--limit` и `--top-k` запрещены. Библиотечный `search()` сохраняет
ранжирование, для нового режима добавлены `firstMatches()` и
`PreparedSearch.firstMatches()`.

Основной показатель **горячего поиска**: `runs[i].timings_ms.lucene_search_ms`.
Это wall time вокруг поиска Lucene с выбранным коллектором через `System.nanoTime()`;
включает rewrite, создание weight/scorer, обход кандидатов и проверку порога до N-го совпадения.
Подготовка query-фичей, explain, чтение ID и текстов в этот показатель не входят.

У каждого измеряемого запуска есть `search_ms` — полное время поиска с выдачей,
и разбиение `timings_ms` (все значения в миллисекундах):

| Поле | Что измеряется |
|---|---|
| `build_query_ms` | Подготовка query-фичей и запроса; в hot-режиме 0, вынесена в `prepare_query_ms` |
| `lucene_search_ms` | Поиск первых N совпадений (или top-K в явном режиме ранжирования) |
| `explain_ms` | 0 для первых N; объяснения оценок только при `--top-k` |
| `fetch_ids_ms` | Чтение сохранённых ID найденных документов |
| `fetch_documents_ms` | Получение title/text; в режиме первых N — непосредственно по Lucene doc ID |
| `other_ms` | Остальная работа внутри общего замера, включая сборку ответа |

Сумма этапов соответствует `search_ms`. JSON-сериализация, печать, передача в notebook,
старт JVM, копирование и открытие индекса сюда не входят. В hot-режиме также исключены
предварительная подготовка и прогрев, для которых выводятся отдельные времена.
`copy_to_ram_ms` и `open_model_and_index_ms` относятся к общей загрузке один раз.
Для совместимости верхнеуровневые `search_ms` и `result` обозначают первый измеренный
запуск. `warmup_queries=1`, `query_count=3`; `active_index` показывает фактически
открытую папку. RAM-копия удаляется после завершения всех запусков.

Notebook выводит ход выполнения сразу и таблицу в секундах. Тексты документов
показываются для первого измеренного запуска; полные выдачи всех трёх есть в `response['runs']`.

Без `--hot true` сохраняется режим с подготовкой внутри каждого запроса;
без `--repeat` выполняется один измеряемый запуск. Без `--ram-root` используется
исходный индекс. Поля по умолчанию `text` и `title` можно изменить через
`--text-field` и `--title-field`. Строгий порог `score > threshold`, пустая выдача допустима.
Индексатор должен быть остановлен: при копировании берётся write lock.

## RAM

128 ГБ на сервере не обязательно доступны процессу JupyterHub. Перед копированием
проверяются свободное место tmpfs, MemAvailable и видимые ограничения cgroup.
При расчёте cgroup учитывается оценка освобождаемого чистого дискового кеша:
`file - shmem - file_dirty - file_writeback - unevictable`, с нижней границей 0.
Поэтому заполненный дисковым кешем контейнер не считается полностью занятым.
Анонимная память, tmpfs, грязные и закреплённые страницы не добавляются в доступную
память. При недоступной/неполной статистике применяется прежняя строгая оценка.
Сохраняются пределы всех видимых родительских cgroup и MemAvailable хоста;

оставляется место под Java heap (`-Xmx4g`) и резерв 12 GiB (`--reserve-gib`).
Резерв — оценка, не гарантия при параллельной нагрузке. Если `/dev/shm` мал,
нужен другой доступный tmpfs нужного размера или изменение лимита администратором.
JAR сам ничего не монтирует и не меняет лимиты сервера.

[Linux tmpfs](https://www.kernel.org/doc/html/latest/filesystems/tmpfs.html)
может использовать swap. Для строго RAM-only эксперимента нужен tmpfs без swap
(опция `noswap`, если поддерживается сервером) или сервер без активного swap.
`-Xmx4g` относится к Java heap: сам индекс хранится в tmpfs, вне heap.

Сборка JAR на машине разработчика:

```bash
mvn -Prunner package
```

Результат: `target/monoforest-0.1.0-SNAPSHOT-runner.jar`.

## Настройки вашего JupyterHub

По вашей диагностике: лимит контейнера 120 GiB, `/dev/shm` — 64 MiB,
а `/run/jupyter-monitor` — tmpfs на 120 GiB. В notebook подставлены ваш индекс,
Java 11 и собственная папка `/run/jupyter-monitor/monoforest-anglukhikhan`.
Используется `-Xmx4g`, чтобы оставить дополнительный запас рядом с индексом 96.46 GiB.

Исправленный JAR выводит в stderr строку `RAM preflight: ... clean file cache included`.
Копирование всё равно требует реально доступных ресурсов; это оценка, а не резервирование.
Не требуется менять conda-среду, писать в `memory.reclaim` или сбрасывать кеш хоста.
Определения полей: [документация cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html).

## Частоты слов обучающих запросов

Исходный `docv2_train_queries.tsv` (12.89 MiB) включён в JAR как ресурс
`/monoforest/docv2_train_queries.tsv`. Это тот же файл, который использовался
локально для QueryMinLogFrequency, QueryMaxLogFrequency и QueryMeanLogFrequency.
Для обычного запуска дополнительно загружать TSV не нужно. При сборке на другом
компьютере в Git должен быть добавлен файл
`src/main/resources/monoforest/docv2_train_queries.tsv`.

Если нужен внешний TSV, укажите JVM option **перед `-jar`**:

```bash
java -Xmx4g -Dmonoforest.queryFrequencyTsv=/path/to/docv2_train_queries.tsv \
  -jar monoforest-0.1.0-SNAPSHOT-runner.jar --index /path/to/index \
  --model /path/to/linear_monomials.json --query "grammar terms medicine"
```

В notebook соответствующая часть `command` выглядит так:

```python
JAVA, f"-Xmx{HEAP}", "-Dmonoforest.queryFrequencyTsv=/path/to/docv2_train_queries.tsv", "-jar", str(JAR),
```

Если указанный внешний файл недоступен, запуск завершается ошибкой, без подмены
его встроенным корпусом. Для моделей с частотными фичами доступность источника
проверяется **до** копирования индекса в RAM. В hot-режиме подсчёт частот входит в
`prepare_query_ms` и выполняется один раз. Без hot-режима он входит в
`build_query_ms` / `search_ms` каждого запроса. Частоты и score не заменяются нулями.
