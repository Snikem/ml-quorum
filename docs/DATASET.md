# Датасет новых фичей: исходные TSV → CSV

Генерация выполняется целиком на Java, нужны JDK и Maven. Источники —
исходные TSV с запросами и JSON документов, которые читали три генератора
из `DatasetOrchestrator.java`. Старые `train.tsv`, `valid.tsv` и
`features_part*.tsv` больше не используются как входные данные.

## Запуск

Откройте `DatasetOrchestrator3.java` и запустите его `main()` в IDE,
как у остальных оркестраторов. Все настройки находятся в начале класса:
`NEGATIVE_INPUT_DIR`, `POSITIVE_INPUT_DIR`, `BM25_INPUT_DIR`, `OUTPUT_DIR`,
`INDEX_DIR`, `TEXT_FIELD`, `PART_COUNT`, `BM25_TOP_N`, `LEGACY_BM25_LIMIT`,
`SPLIT_SEED`, `TRAIN_QUERY_FRACTION`.
Аргументы командной строки, внешний запускной скрипт и `.env` для настройки
этого оркестратора не используются.
Результат: `train.csv`, `valid.csv`, `feature_names.txt`, `feature_schema.csv`
и `manifest.json`. Выходная папка не перезаписывается. Полный расчёт MS MARCO
пользователь запускает самостоятельно.

## Точные исходные пути из старой генерации

| Старый вызов | Исходная папка | Файлы |
| --- | --- | --- |
| `MakeRandomNegativeStream.getStream(1f, ...)` | `/Volumes/Ex_Volume/DatasetStream/randomNegative/negative_qrels_with_queries` | `qrels_doc_00_with_docs.tsv` … `qrels_doc_59_with_docs.tsv` |
| `MakePositiveStream.getStream(1f, ...)` | `/Volumes/Ex_Volume/DatasetStream/onlyPositive/qrels_with_queries_train` | `qrels_doc_00_with_docs.tsv` … `qrels_doc_59_with_docs.tsv` |
| `MakeBm25Stream.getStream(1f, ...)` | `/Volumes/Ex_Volume/DatasetStream/bm_25_streamTop100` | `qrels_final_00.tsv` … `qrels_final_59.tsv` |

Порядок: случайные негативы, позитивы, BM25; внутри каждого источника
файлы 00–59, строки в исходном порядке. Multiplicator=1.0 соответствует
60 файлам каждого источника. В старом `DatasetOrchestrator.java` вызовы
первых двух генераторов закомментированы; новый генератор включает все три,
чтобы собрать полный обучающий набор, описанный в исходной цепочке.

Случайные негативы и позитивы:

```text
query<TAB>0<TAB>doc_id<TAB>label<TAB>JSON
```

BM25-негативы:

```text
query<TAB>0<TAB>doc_id<TAB>JSON<TAB>rank
```

В первых двух источниках метка берётся из четвёртой колонки; у BM25 метка 0.
JSON может быть обычным или обёрнутым в CSV-кавычки с удвоенными кавычками
внутри. Из JSON берутся `title` и `body`, отсутствующие поля становятся
пустыми строками, как в старом коде. `headings` не добавляется.

Новый код не вызывает `findAndSaveCandidates`: BM25-кандидаты уже находятся
в `qrels_final_XX.tsv`. Поэтому случайный отбор top-5000 с десятью попытками,
который выполнялся на более раннем этапе подготовки, заново не запускается.

## Сборка train/valid

После чтения исходных пар применяется логика **DatasetOrchestrator2**:

| Параметр | Значение по умолчанию |
| --- | --- |
| Первый и второй потоки | Все строки |
| BM25-поток | Первые 100 002 строки суммарно по файлам |
| Группировка | Исходный текст запроса |
| Перемешивание | Ключи `HashMap`, seed 42 |
| Train | `floor(0.95 * число запросов)` групп |
| Valid | Остальные группы |
| Порядок внутри группы | Исходный порядок строк; дубликаты сохраняются |
| Выходная папка | `/Volumes/Ex_Volume/DatasetStream/totalSet/new_features` |

100 002 — фактический лимит старого `DatasetOrchestrator2`: условие
`counted > 100000` проверялось после добавления строки. Теперь лишняя часть
BM25-потока не пересчитывается, поскольку в итоговый split она всё равно
не попадала. Это не полный дамп третьего потока. `LEGACY_BM25_LIMIT = -1` включает
все его строки и меняет состав датасета.

На диск временно записываются выбранные сырые пары, в RAM хранятся запросы
и смещения. Фичи вычисляются при чтении сгруппированных пар, чтобы запросные
фичи и BM25 top-N считать один раз на группу. Временный файл содержит тексты
выбранных документов; необходимое место зависит от их размера. После
успешного расчёта он удаляется, CSV публикуются под окончательным именем.
При ошибке папка `new_features.building-*` остаётся для диагностики.

Как в старых генераторах, отсутствующие отдельные shard-файлы пропускаются
с сообщением и фиксируются в manifest. Недоступная папка или полностью пустой
обязательный поток завершают запуск ошибкой. Битые строки и ошибки расчёта
теперь останавливают генерацию с контекстом, а не молча теряют примеры.

## Фичи и индекс

Все фичи считаются через `calculateAllFeaturesInFamily`, без `buildLuceneQuery`.
Документы берутся **только из JSON исходных TSV**: поиска документов по ID
и чтения stored title/body из Lucene нет.

По указанию пользователя оставлен индекс
`/Volumes/Ex_Volume/msmarcoProcces/lucene_index_positions` в константе `INDEX_DIR`.
Он используется для статистики BM25/TF-IDF и поиска BM25 top-N. У BM25
`k1=1.2`, `b=0.75`, как в старом коде. Фичи остальных семейств считаются локально
по текстам и токенам. Для запросных фичей сохраняется исходная строка;
для совместных используется `WhitespaceAnalyzer`, как в новой индексации.

Включены все 17 новых семейств, 35 фичей при N=3:

- QueryWords, QueryCharacters, QueryNumbers, QueryNouns, QueryFrequency;
- DocumentWords, DocumentCharacters, DocumentNumbers, DocumentParagraphs,
  DocumentSize, DocumentUrls;
- BM25, TFIDF, ExactMatch, TitleExactMatch, UnorderedWindow, BM25TopScores.

N=3 — отдельный параметр нового семейства BM25TopScores, не лимит негативов.
Входной rank не входит в новые семейства и не добавляется в CSV.

## Формат CSV и настройки

UTF-8, запятая между колонками, точка в дробных числах. Первая строка:
`label,query,doc_id,` и далее точные имена фичей. Запятые, кавычки и переводы
строк внутри текстовых значений экранируются по правилам CSV. Значения фичей
проверяются на NaN/Infinity и соответствие схеме.

Для pandas: `pd.read_csv(path, keep_default_na=False, dtype={'query': str,
'doc_id': str})`. Названия колонок читаются автоматически; текст `NA` и
начальные нули в ID сохраняются. Фичи — колонки без `label`, `query`, `doc_id`.

Пути и числовые параметры меняются непосредственно в константах Java-класса.
Режимы чтения готовых train/valid и старых фичей удалены.
